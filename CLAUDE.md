# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RangeBoard: a local-first web "integrated air defense whiteboard" for Counter-UAS test-and-evaluation planning. Infinite meter-scaled canvas with sensor footprints, kill-chain links, threat flight paths, test cards, timeline playback, and engagement analysis. Single user, no backend.

## Commands

```
npm run dev              # Vite dev server (picks next port if busy)
npm run test             # vitest run (all tests)
npx vitest run src/geometry   # one test file/dir
npm run build            # tsc -b && vite build (type-check + bundle)
npm run lint             # oxlint
```

Deliberately NOT tldraw (license + document-model friction). Stack: React 19, react-konva, zustand, vitest. Playwright is a devDependency for scripted browser verification only.

## Core invariants (breaking these breaks the app)

- **World frame:** meters. +x east, **+y south** (screen-down). Heading 0 = north (up), clockwise degrees. All conversions live in `src/geometry/geo.ts` (pure, fully unit-tested). North on screen is negative y: `bearingDeg({0,0},{0,-100}) === 0`.
- **Camera:** `{x, y, scale}` = Konva Stage pixel offset + **pixels per meter**. World→screen: `sx = wx*scale + x`. Konva layer children are positioned in meters; the Stage transform does the scaling.
- **Single source of truth:** the `Scenario` object in `src/state/store.ts` (zustand). The Konva tree is a pure view of it. Never store derived state (positions at time t, detections) back into the scenario.
- **Playback is derived:** entity position at sim time = `posAtTime(path, speed, delay, t)` computed in `src/playback/sim.ts` from the base scenario. `playback.simTimeS` is the only mutable playback state.
- **Undo model:** `mutate(fn)` inside the store pushes a full scenario snapshot to `past` (cap 100) and clears `future`. Only scenario changes are undoable; camera/selection/ui are not. Any new scenario-touching action must go through `mutate`, not `set`.
- **Schema:** `Scenario.schemaVersion = 1`. Autosave key `rangeboard.scenario.v1` in localStorage; `fillScenario` (persist.ts) spreads the save over `emptyScenario()` and deep-fills one level into `environment`, `requirements`, `doctrine`, `mcdaWeights`, `underlay`, and `raid`. If you add a top-level field or a field in one of those objects, add a default in `emptyScenario()` and the round-trip stays valid; a new nested object needs its own line in `fillScenario`. Bump the version only for breaking shape changes. A save that exists but cannot load is copied to `rangeboard.scenario.recovered.<ms>` before anything writes (T&E: `rangeboard.te.recovered.<ms>`). `Scenario.deletedSeedIds` holds builtin model and preset ids the user deleted; the seed merge on load skips them. `loadScenario` (built on `replaceScenario`) is the one load path for the startup autosave and file import; `replaceScenario` clears history, selection, every draft field and the tool.
- **Storage keys live in `src/io/storageKeys.ts`**; never rename one. View state that is not in the `Scenario`: `rangeboard.view.v1` (camera, basemap, right tab, workspace; `src/io/viewState.ts`, written eagerly by the setters), `rangeboard.runseq.v1` (run sequence the next startup issues: only a manual `resetRun` advances the sequence, a configuration change or a load keeps it and marks the run invalid). Autosave status is the top-level `save` slice, not `ui`.

Data flow for a click/drag: Konva event → store action → new scenario → React re-render of layers. Drag-in-progress is Konva-native; the store is updated once on `dragend`.

## Konva conventions used everywhere

- Constant screen-size strokes: `strokeScaleEnabled={false}` (stroke width and dash are then in px).
- Constant screen-size icons/labels: wrap in a Group with `scale={1/camera.scale}`; inner units are px.
- Footprints and other large fills must be `listening={false}` or they swallow stage clicks.
- Hit tolerance for thin lines with `strokeScaleEnabled={false}`: `hitStrokeWidth={n}` (screen px — the hit stroke ignores the stage transform too; dividing by camera.scale inflates it to hundreds of px).
- Drawing tools do not use Konva drag: stage `draggable` only when `ui.tool === 'select'`; other tools consume plain clicks (`ui.draftPoints` holds the rubber-band draft).

## Domain semantics worth knowing

- `SpecModel` (library entry) vs `Entity` (canvas instance referencing `specId`). Entities survive model deletion (`specId → null`). Custom models: `builtin: false`; duplicate-and-edit supported.
- Kill chain = `Connection` list; `sim.killChainConnected` accepts sensor→C2→effector or direct sensor→effector.
- `assessThreat` statuses: `no-path | never-detected | not-confirmed | detect-only | no-kill-chain | window-too-short | weapons-hold | engageable`. Engagement windows are gated by `Scenario.roe` (`free` = first detection, `tight` default = hostile classification, `hold` = none); the derived classification ladder (`pending → unknown → suspected → hostile`) lives in `sim.ts`. Legacy `engageOn` saves migrate on load in `persist.ts` (`detected` → `free`, `confirmed` → `tight`). `not-confirmed` = tight ROE, never reached hostile.
- **Arrival vs closest approach** (two different questions, never merge them). ARRIVAL (`ThreatAssessment.arrivalS`) = the first sample the threat is inside an asset's `Entity.defendedRadiusM` (`DEFAULT_DEFENDED_RADIUS_M` 500 m when unset; set it in the Inspector). Null when the threat never crosses one, and null when no asset is placed. CLOSEST APPROACH (`cpaS` / `cpaDistanceM` / `cpaAssetId`) is pure geometry to the nearest asset and exists whenever any asset is placed, so a fly-by that turns away has a CPA and no arrival. Warning time (`warningS`) = arrival minus first detection, so it is null without an arrival. `assetId` / `closestApproachM` are the old names for the CPA pair, kept for older callers.
- **Raid partition** (`src/playback/attrition.ts`): every ship lands in exactly one bucket and `expectedKills + expectedLeakers + expectedNoArrival === raidSize`. `expectedKills` is PRE-ARRIVAL kill mass only (the defeat number). `expectedLateKills` is destruction whose effect landed after arrival: real, but too late to defend, so it is a sub-measure of the leaker mass and never a deduction from it. `expectedLeakers` counts only threats that actually crossed a boundary; `expectedNoArrival` takes fly-bys and every ship in an asset-free run. Display `totals.reportedLeakers` (null when no asset exists, render a dash), never `expectedLeakers`, which is a partition term.
- **Expenditure is three channels**, independent of the hard/soft kill channel (`isHardKill`): `shotsFired` = KINETIC (interceptor, gun, net), `deSalvos` = DIRECTED ENERGY (de, hpm), `jamSalvos` = EW (jammer). `expenditureChannel()` answers what a salvo SPENT; `isHardKill()` answers what it DESTROYS. DE and HPM are hard kills that fire no round, so they must never be counted as kinetic. `TrackFileState` mirrors the three as `kineticSalvos` / `deSalvos` / `jamSalvos`.
- **Fire doctrine** (`Scenario.doctrine`, `FireDoctrine` in types.ts, default ENABLED). The sequence is detect -> track -> identify -> target -> engage -> assess. GATE (sim.ts), PER EFFECTOR and route-aware: a shot needs a stable fire-control track from a sensor ROUTED to that effector (`KillChainRoute.sourceSensorIds`; a firm track that reaches no shooter authorizes nothing, status `no-stable-track`), hostile ID on the ladder, then the declaration dwell (`declareHostileS`, halved when two phenomenologies confirm before declaration starts); ROE free/tight converge, hold still blocks. `effectorGates[].gateS` is that engagement authority; `effectorGates[].readyS` = gateS + route latency + the effector's TARGET dwell (`targetSFor`: spec `EffectorSpec.targetS`, else `TARGET_S` by effector type, else `doctrine.targetS`) and is the first possible release. Under doctrine `windowS` opens at readyS, so the TGT rung and the `targeted` phase mean release-ready. FIRE DISTRIBUTION (attrition.ts doctrine pass): shoot-look-shoot — one kill salvo in flight per ship plus a post-effect BDA dwell (`ShipState.holdUntilS`), best predicted per-shot Pk wins the assignment (near-ties prefer unlimited, then fuller magazines). LAUNCH POINT is `doctrine.launchPolicy` (`launchPolicyReleases`, evaluated at the effect point): `max-range` fires at the first opportunity, `range-fraction` once the intercept is inside `launchRangeFraction` x max range (default 2/3), `pk-commit` (default) once Pk reaches the effector commit Pk, `latest` never volunteers. Every policy fires at the deadline that preserves `opportunities` engagement cycles before arrival (CPA for a fly-by), capped by the closing in-range window. `LAUNCH_POLICIES` in doctrineFactors.ts is the one label/hint table. **Per-system factors live in `src/analysis/doctrineFactors.ts`**: track initiation by sensor role (`TRACK_INIT_S`, spec override `SensorSpec.trackInitS`, the fallback path under the scan model), target dwell, BDA and commit Pk by effector type (`TARGET_S`, `BDA_S`, `PK_COMMIT`, spec overrides `EffectorSpec.targetS` / `bdaS` / `commitPk`), default kill-chain hop latency for links with no `latencyS` (doctrine only; legacy keeps unset = 0). The scenario-level `trackFirmS`/`targetS`/`bdaS`/`pkCommit` are last-resort fallbacks; the Analysis panel Fire doctrine section edits only the fields that bind scenario-wide (policy, fraction, declaration dwell, depth). Jammers always keep the legacy path: a dwell is illumination, not a round. TRACK INITIATION has two paths and `scanRateSFor` is the ONE resolver: a radar with a finite positive `SensorSpec.updateRateS` runs the SCAN MODEL, every other radar and every EO/IR keeps the `TRACK_INIT_S` role table (`trackInitSFor`), and RF and acoustic sensors initiate no fire-control track. Scan model (sim.ts): scans fall at `firstDetectS + k * updateRateS`, each snapped FORWARD to the DT grid, and a rate below DT counts one scan per step; a scan detects when the per-step hit test passed, and its Pd is the probe value, so with no Pd model it is 1 on a hit and 0 on a miss and M-of-N degenerates to a count rule; TRACK starts at the first scan with at least M of the last N scans detected AND `mOfN(mean Pd, M, N) >= pdTrackCumulative` (`pdTrackCumulativeOf`, guarded, read through the `{ ...DEFAULT_REQUIREMENT_THRESHOLDS, ...scenario.requirements }` spread, never an engine constant). M, N and the drop count are `TRACK_INIT_M` 3, `TRACK_INIT_N` 5 and `TRACK_DROP_MISSES` 5 (PF), overridden per spec by `trackInitM` / `trackInitN` / `trackDropMisses` through `trackInitMFor` / `trackInitNFor` / `trackDropMissesFor`. Between scans the hold carries the last scan result. A missed scan COASTS: held for `intervals`, `heldSamples` and `trackSamples` continuity, recorded in `coastIntervals`, and invisible to `stepTechs`, the classification ladder, `firstConfirmS` and `lastDetectS`, because a coast is extrapolation and not a measurement. The track DROPS at the `trackDropMisses`-th consecutive miss and `intervals` split there. A hit of a scan radar at a non-scan step is ignored. `SensorObservation.trackInitAtS` is the ONE field consumers read: written once on both paths, never rewritten after a drop, null for RF and acoustic. `TrackFileState.coasting` is true when the track is held and every holding sensor is inside a coast interval; the readout phase pill then reads COAST in the phase color and `PHASE_STYLE` gains NO new phase. Giraffe 1X states `updateRateS: 1` with a sourced provenance row (basis `reference`, Saab product page). `stableTrackAtS` is the earliest `trackInitAtS` over the radar and EO/IR observations, computed on every assessment (informative when doctrine is off), and the per-effector gate reads that same per-sensor map; `declaredHostileAtS` is the earliest gate. DISABLED = legacy instant release (the ROE gate alone opens the window, every ready effector volleys); keep it for regression, and pin legacy test fixtures with an explicit `doctrine.enabled = false`. Persist migration (`fillDoctrine`): a saved doctrine record with no `launchPolicy` predates this default and adopts `enabled: true`; a record with a `launchPolicy` keeps its flag.
- **Route latency is charged from the ROE gate**, not from T0: an effector is a candidate for a threat only from `gateS +` that (effector, threat) kill-chain route latency, so a late gate still pays the full delay. Assignment-to-effect latency is separate: a salvo fired at `tS` lands at `tEffectS = tS + engageTimeS`, expenditure counts at `tS`, kill and jam mass count at `tEffectS`.
- **Run validity has one source of truth:** `src/analysis/runValidity.ts` (`assessRunValidity`). Findings are `invalidating` (the named gates cannot be scored for the named tracks; a result the run cannot support is neither a pass nor a fail) or `limiting` (scored, with a caveat). The requirement gates, the exported record, and the toolbar spawn-in-ring chip all derive from it, so they can never disagree. Derived live, never stored on the `Scenario`.
- **Requirement thresholds are test-defined, not engine constants:** `Scenario.requirements` (`RequirementThresholds`, defaults in `DEFAULT_REQUIREMENT_THRESHOLDS`) holds what the test asks the system to meet. Never set a gate threshold to an engine constant: the attrition model stops firing at `SHIP_DEAD_BELOW`, so a requirement at that value passes itself by construction.
- Sensor physics live in `src/analysis/sensorEnv.ts` (COURAGEOUS-based planning factors). One shape for every technology: the placard range is quoted against a REFERENCE target, the range against another target follows a physical law, group tiers fill blanks and are labeled PF (`src/model/rcsFactors.ts`, `src/model/signatureFactors.ts`), a sourced datasheet value overrides the tier, and `SensorSpec.rangeBasis: 'planning'` (role-table or representative ring, no stated target) turns target scaling off. RADAR: fourth root of `rcsM2 / refRcsM2` (`rcsRangeFactor`), capped by `instrumentedRangeM`. EO/IR: linear in `spanM / refSpanM` (Johnson criteria, `eoRangeFactor`), times `IR_SIGNATURE_FACTOR[irSignature]` when the thermal channel carries (`eoBand` thermal, or dual at night), night cuts a visible-only sensor to `NIGHT_VISIBLE_FACTOR`, and the result is capped at the meteorological visibility (`EnvironmentSpec.visibilityM`, else `VISIBILITY_BY_PRECIP`; Koschmieder). ACOUSTIC: solve `20 log10(R/Rref) + ALPHA_DB_PER_KM (R - Rref)/1000 = acousticDb - refAcousticDb` (`acousticSolveM`), then wind and urban multiply. RF: no target scaling; `rfCanHear` needs an emitting link band inside `SensorSpec.rfBands` (GNSS never counts), and a published `urbanRangeM` replaces the generic urban multiplier. Target laws apply with the environment toggle off; weather terms follow it. RADAR Pd: the placard is one point on a Pd curve, so single-scan probability of detection follows from the radar range equation. `radarCalibration(spec)` reads r0 = `detectRangeM`, rcs0 = `refRcsM2For(spec)`, pd0 = `SensorSpec.placardPd` else `PLACARD_PD` 0.5, pfa = `SensorSpec.pfa` else `PLACARD_PFA` 1e-6, and case `PLACARD_SWERLING` 1 (all PF until slice 9; a recorded Pd or Pfa outside (0, 1) falls back to the planning factor). SNR at range = snr0 x (rcs / rcs0) x (r0 / R)^4 x m^4, so the environment multiplier m enters as the FOURTH POWER. The closed forms live in `src/analysis/radarPd.ts` (`pdFromSnr`, `snrForPd`, `pdAtRange`, `rangeForPd`, `mOfN`): Swerling 1 is `Pfa^(1/(1+SNR))`, Swerling 0 is Albersheim, Swerling 3 is the Mahafza single-pulse form pinned against Marcum-Q integration. The target case is `swerlingFor(uas)` (`src/model/rcsFactors.ts`): `UasSpec.swerling`, else `SWERLING_BY_AIRFRAME` (fixed-wing 3, every other airframe 1, PF). `radarPdAt(spec, env, target, slantM)` is the ONE Pd evaluation: null for a non-radar, a `rangeBasis: 'planning'` sensor or no target, 0 beyond `instrumentedRangeM`. `effectiveDetectRangeM(spec, env, target?, pd?)` sends a sourced radar with a target through `rangeForPd` at `pd`, default the placard Pd, so with matching Swerling cases it is exactly the fourth-root law, and a fixed-wing target (case 3) sits about 4.8 percent farther at Pd 0.5 than that law. `pdContoursM(spec, env, target, pds)` returns the contour slant ranges; `FootprintLayer` ground projects and draws them as the Pd contours. `rangeBasis: 'planning'` skips the Pd model as it skips RCS scaling. The cue rule is role-aware (`eoIrNeedsCue`: classification, fire-control, tracking, target-acquisition need a cue; surveillance and early-warning EO/IR search on their own). `sensorHoldGate(spec, target)` (`ok | needs-cue | rf-silent | rf-band | no-range`) is the ONE gate the sweep, the board and the inspector share. In the sweep, `admittedSlantsM` is the one member loop for the hit test and the Pd probe; the radar Pd branch of `sensorHit` detects a member when `radarPdAt` reaches `requirements.pdDetect`, and every other path keeps the range test and returns null when the effective range is not > 0. `DetectionHit.pd` is the Pd of the nearest detected member (null on the range path); `SensorObservation.pdSeries` exists only for a radar with a Pd model and holds one value per DT step from `firstDetectS` to the path end, below-threshold and post-detection steps included, read at the nearest admitted member and 0 when none is admitted. `RequirementThresholds.pdDetect` (0.5) and `pdTrackCumulative` (0.9, the scan-model TRACK threshold in sim.ts) are test-defined: every reader takes them as `{ ...DEFAULT_REQUIREMENT_THRESHOLDS, ...scenario.requirements }` and never as an engine constant, the Analysis panel "Requirement thresholds" section edits them, and `fillScenario` fills them from the defaults for an older save. The Inspector against-threats list, the solid board contour and the envelope band all read at `pdDetect`; the placard ring reads the placard Pd. The Inspector shows placard Pd, placard Pfa, the placard case and the threat fluctuation model with PF tags from `basisFor`; the placard rows read `radarCalibration`, so a recorded value the engine replaced shows PF. The LibraryEditor edits placard Pd, Pfa and the fluctuation model. The board draws the placard ring at the placard range, never scaled; with a threat selected the Pd contours draw in front of it and it goes dotted. Jammers cannot affect `fiber`/`inertial`/`optical` threats, and `effectorWindows` uses `effectiveJamRangeM` for jammers. `SensorSpec.resolutionM` merges formations spaced below it into one track (`swarmMerged`).
- **Jam physics live in `src/analysis/ewPhysics.ts`** (planning factors). A jam holds only when the physics close: nav-mode gate (`jammable`), band coverage (`EffectorSpec.jamBands` vs the target's `linkBands`, nav-mode default when absent), off-boresight taper inside the transmit cone, and power/range closure (`eirpW` below `ratedEirpW` shrinks the placard `maxRangeM` by sqrt of the power ratio; `UasSpec.jamResistDb` costs range the same way). Jammer Pk = base Pk x that factor and takes NO kinetic size/evasion penalty — links do not jink. `assessThreat` drops a jammer from a threat's effector set on band mismatch; attrition skips ships the physics cannot reach. Board symbology: jammer footprints are gradient "flashlight" cones (FootprintLayer, length = power-scaled effective range); A 'continue' jam is ILLUMINATION, not damage: the hold (`JamHold` in attrition.ts) is bound to the jammer's in-range interval that produced the dwells, lapses the moment the target flies out of the beam (kill-Pk degrade included), and re-entry starts from zero; `continueJamProb` reads at arrival, else CPA, else the last dwell. An effectively jammed track (`TrackFileState.jammedNow`: live EW dwell or 'continue' jam probability >= JAMMED_AT, both illumination-bound) draws a cyan diamond + J in `EW_JAM_COLOR` (one definition, trackState.ts, shared with the jam beam) and an EW-only engagement suppresses the target brackets.
- Threat tactics: `src/playback/tactics.ts` (THREAT_TACTICS, study-coded, platform pairings by seed designator). The raid builder arms a ui-only `raidDraft` and `commitRaid` creates entities + paths + waves in ONE `mutate()` (single undo); spawn standoff clears every enabled sensor ring measured from the sensor position.
- Threat WEZ + I&W: weapon fields on `UasSpec` (warheadKg, effectRadiusM, standoffRangeM, weaponProfile); `effectRadiusM` values are PLANNING FACTORS (`src/model/weaponFactors.ts`) — the threat study declines lethal radii, so label them PF in UI. `src/analysis/impact.ts` derives WEZ geometry (coincident impact circles merge with a count) and leaker severity; `engagementPicture` WeakMap-caches one sweep per scenario object. `ui.layers.threatWez` is a render toggle (View menu, right-click Display flyout, Analysis header, command palette).
- **Altitude and slant range:** one constant altitude per placed threat, `Entity.altitudeFt` (feet AGL, unchanged along the path). Placement seeds it from the model `threatProfile.altitudeFt` (drop, integration placement, raid builder in `src/state/store.ts`). `threatAltitudeFt(scenario, uas)` in `src/playback/sim.ts` is the ONE resolver: the entity value, else the threat profile, else the `UasSpec.altBandFt` midpoint, else 0. An old save has no field and resolves at read time, so nothing migrates and `fillScenario` gets no line. Sensors and effectors carry `mountHeightM`, else `MOUNT_HEIGHT_M` (4 m, a planning factor; no seed model states one); `mountHeightOf(spec)` is the one resolver. `src/geometry/slant.ts` is the pure geometry: `slantRangeM`, `groundRangeM` (clamped at 0), `elevationDeg`, `radioHorizonM` (4/3 earth, `4120 * (sqrt(h1) + sqrt(h2))`). VERTICAL GATE in `sensorEnv.ts`: `sensorGeometryGate` (`ok | below-horizon | elevation | ceiling`) runs per member AFTER `sensorHoldGate` and BEFORE the range test. Horizon applies to radar, rf and eo-ir, never to acoustic; elevation applies only when `SensorSpec.elevationDeg` is recorded; ceiling applies only when `maxAltitudeFt` is recorded. `effectorGeometryGate` (`ok | ceiling`) is the effector half; a jammer takes the slant range but no ceiling. `FT_TO_M` is the one conversion. SLANT RANGE, not ground range, feeds the sensor detect and classify tests (`DetectionHit.slantM`, `SensorObservation.minSlantM`), the effector window in `assessThreat`, both `inEnvelope` closures in `src/playback/attrition.ts`, and `distanceFalloff`. The azimuth wedge stays a ground-plane bearing test (`inWedge`, infinite range). The board ground projects every selected-threat ring through `groundRangeM` (the Pd contours, the classify ring and the kinetic effector rings); the placard ring is unprojected. STAYS OUT: terrain, per-waypoint altitude, and any refraction beyond the 4/3 factor. PROVENANCE: `SpecModel.provenance` (`Provenance[]`) records field, value, source, url, date and basis; `basisFor(model, field)` returns that basis, else `pf`, and the UI shows the PF tag. The "recorded, not modeled" markers are gone from the Inspector, the LibraryEditor and the TrackFileReadout.
- **Symbology contract** (one definition per fact, never a second hardcoded copy). MIL-STD-2525 split: the FRAME carries affiliation, an inner ICON carries function. `src/panels/Glyph.tsx` holds `FRAME_FOR` (friend rounded-top rectangle for sensor/effector/c2/asset, hostile diamond for uas, neutral square for marker), `FUNCTION_LETTER`, and `FRIEND_FRAME_D`; `EntityLayer` draws the same constants in Konva, so the palette, the library lists and the board agree by construction. `PHASE_STYLE` in `src/playback/trackState.ts` is the single source for track phase COLOR and LABEL (ghost reads DEFEATED), shared by the canvas ring, the board tag and the telemetry pill. Canvas entity labels draw `boardDesignator(entity.name)` from `src/canvas/labelLayout.ts`; anything stacked under a label measures with `labelLineCount` on that same drawn string.
- **Layer visibility:** `ui.layers` (`LayerVisibility`, 17 boolean keys; `sensorFootprints` and `effectorEnvelopes` are gone, `savedLayers()` migrates them to `sensorPlacard` and `effectorMaxRange` and then drops both old keys). Actions are `setLayer`, `toggleLayer`, and `applyLayerPreset` (`full | planning | engagement | clean`). The DEFAULT layer state is `DEFAULT_LAYERS`, NOT the `full` preset: the placard ring and the effector max range on, the other five ring keys off. Presets: `full` every ring key, `planning` placard, envelope, effector max and min, `engagement` placard, effector max and doctrinal, `clean` none. SEVEN RING KEYS (`RingKey`, `RING_KEYS` = `SENSOR_RING_KEYS` + `EFFECTOR_RING_KEYS`): `sensorPlacard` the detect ring at the reference condition, `sensorEnvelope` a fill-only band between the shortest and the longest effective detect range over the placed threats, `sensorPdContours` the Pd rings against the selected threat, `classifyRings` the classification range, `effectorMaxRange` and `effectorMinRange` the weapon envelope, `effectorDoctrinal` the release and commit-Pk rings for the selected threat. PER-ENTITY OVERRIDES: `ui.ringOverrides` (`RingOverrides`, one partial ring-key map per entity id) under `RINGS_KEY` (`rangeboard.rings.v1`, `savedRingOverrides` / `writeRingOverrides` in `src/io/viewState.ts`); `setRingOverride(entityId, key, on | null)` uses `set` and never pushes undo, `null` drops the entity back to the layer flag; `ringVisible(ui, entityId, key)` is the ONE resolver every consumer reads; overrides prune to the live entity ids on `replaceScenario` and `deleteSelection`, never in the constructor. Effector rings draw in `--danger` through `EFFECTOR_RING_COLOR`; a jammer keeps its entity-color flashlight cone. `src/canvas/layers/footprintStyle.ts` is the ONE style source: `RING_STYLE` (dash, width, fill alpha and ink per key), the dash constants, `sensorRingStyle`, `effectorRingStyle`, `envelopeBandM`, `commitRangeM`, `releaseRangeM`, `kineticPkPenalty`, `PD_CONTOUR_HIGH`. The Pd contours read at `requirements.pdDetect` (solid) and `PD_CONTOUR_HIGH` 0.9 (dashed), for the `held` and `cued` kinds only. A coincident effector ring draws once: release under commit for `pk-commit`, release under max for `max-range`, commit under max when the effector commits everywhere, and `latest` volunteers no release ring. Only a selected-threat ring carries a LABEL (the two Pd contours, release, commit Pk). The controls are the View menu Sensor and Effector groups, the right-click Rings flyout (tri-state, plus Reset to global), the Inspector Rings section, and one command palette entry per key; every ring name and hint comes from `src/panels/ringLabels.ts` (`RING_LABELS`, `RING_HINTS`). This is view state. The setters write the flags to `rangeboard.layers.v1`, `savedLayers()` spreads the stored value over `DEFAULT_LAYERS` on load, undo never touches either map, and neither enters the `Scenario`. Each Konva layer reads its own flag and returns `null`; `CanvasStage` does no gating.
- `src/analysis/mcda.ts` scores a configuration 0-100 from `Scenario.mcdaWeights`; pinned results live in `Scenario.scorecards`. Card templates and the standard covariate checklist live in `src/model/seedCards.ts`.
- Basemap modes (`canvas | sat | airspace`) are render toggles only — never move data. Sat underlay scale is set by two-point calibration, which scales the image about point A.
- Test cards follow the Field Guide standard card; `linkedEntityIds` drive the cyan on-canvas highlight when a card is selected.

## T&E Operations module (src/te/)

- Second workspace ("T&E Ops" toggle in the toolbar): end-to-end C-UAS test campaigns from customer request to delivered evidence. Spec sources: `docs/te-plan.md` and the four MASTER-*.md files in `docs/te-compilation/`.
- **Separate store, no undo:** `src/te/state/teStore.ts` (zustand), persisted at `rangeboard.te.v1`. T&E records are versioned and append-only by doctrine (runs never renumber; issued cards freeze; changes create new versions), so undo does not apply. Never embed campaign data in `Scenario`.
- IDs follow `VLK-<code>-<type>-<seq>` (`src/te/model/ids.ts`); versions live on the record, not in the id. Cards use `id` (unique per version record) + `cardCode` (shared across versions).
- Gates live in `src/te/validate.ts` (pocket rules: no issued card no run, no validity status no analysis, no traceability no finding). `issueCard` enforces blockers in the store.
- Calc engine `src/te/calc/` is pure TS, fixture-tested from MASTER-CALCULATIONS.md. Measure labels suppress pass/fail unless `thresholdApproved`.
- Seeds `src/te/seed/`: measure dictionary, checklist templates, card templates, vignettes, question banks, and `buildJiatf401()` (demo campaign, `illustrative: true`).

## Design system (src/index.css)

- **Tokens, not literals.** `:root` holds two layers: a graphite ramp (`--surface-*`, `--border-*`, `--text-*`, `--status-*`) and short aliases (`--bg`, `--text`, `--border`, `--accent`, …) that the older rules in the sheet already use. New rules read the semantic names. Spacing comes from `--space-1`…`--space-6` plus `--panel-pad` (14 px, the right panel's horizontal padding line); motion from `--dur-fast` / `--dur`. `--border-control` (0.34 alpha) is the boundary of an interactive control and exists because WCAG 1.4.11 needs 3:1 there; `--border-default` and `--border-subtle` are for decorative hairlines and must not be used on an input.
- **Monospace is machine data only:** ids, coordinates, timestamps, units, keyboard keys, numeric readouts, and fixed abbreviation codes (DOC/PROB, the D/TRK/ID/TGT/ENG/FX stage ladder). Interface chrome (tabs, section labels, field labels, buttons, prose) is `--font-ui`. Prose that happens to carry a number is sans; mark the number with `.num` for tabular figures.
- **Chart kit tokens** `--chart-1` to `--chart-5` (`#3987e5`, `#d95926`, `#199e70`, `#c98500`, `#d55181`) are the five categorical series hues in `:root`. `trackSlots` in `src/analysis/series.ts` gives a track its slot by first detection and never moves it, so a filter does not recolor the chart; the sixth track and beyond fold into `--text-dim`. The status colors (`--danger`, `--good`, `--warn`) never color a series, only a mark. `src/charts/tokens.ts` holds `TOKEN_FALLBACK`, which must stay equal to the sheet (a test reads `index.css` and proves it), because static markup and node have no `document`. `getComputedStyle` is read once per chart render (`readTokens` inside a `useMemo`), never per point. Axis tick labels are `--font-mono` 10 px; series labels, the legend and the tooltip are `--font-ui`. The playhead is a `ReferenceLine` driven by the `tS` prop, so no chart runs a timer. `DT` is exported from `src/playback/sim.ts` and `tickStepS` lives in `src/charts/timeAxis.ts`, one source each.
- **Type floor is 10 px.** One exception: `.threat-stage` / `.threat-data-stages span` at 7.5 px, because a 6-column ladder in a 320 px panel truncates operational data at any larger size.
- **Separators, not cards.** Hierarchy comes from surface tone, spacing, typography, a 1 px rule and interaction state. `--radius` is 3 px and nothing exceeds it. The only drop shadows are `--shadow-float` (menus, dialogs, the command palette), `--shadow-pop` (tooltips, popovers) and the one directional wash on `.right-panel`.
- **Inspector kit** `src/panels/inspector/kit.tsx`: `Section`, `Row`, `ObjectHeader`, `Status`, `EmptyState`, `Kbd`, `ShortcutList`, `Actions`. A read-only property is always a `Row` (label left, value right, tabular numerals, `mono` for machine data, `unit` secondary). `<div className="inspector-body insp">` gives a section-driven body (sections own their rhythm); plain `inspector-body` keeps the gap-driven stack the other three tabs use.
- The tab bar in `App.tsx` follows the ARIA tabs pattern (roving tabindex, arrow/Home/End). `.right-resizer` is a `role="separator"` and is keyboard-operable.

## Testing and verification

- Unit tests colocate as `*.test.ts` next to source (geometry, store). Keep geometry/store logic in pure TS so it stays testable without a DOM.
- Dev builds expose `window.__store` (the zustand hook) — scripted browser checks drive real store actions and assert state. Pattern: Playwright headless against the dev server; screenshots for visual confirmation.
- Keyboard map (in `App.tsx`): Cmd+Z / Shift+Cmd+Z, Delete, Esc (cancel draft + tool→select), Enter (finish boundary/path), Space (play/pause). Shortcuts are suppressed while typing in inputs.
