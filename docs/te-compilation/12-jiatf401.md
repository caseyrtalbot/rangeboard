### 1.7 Question / hypothesis / prediction records (Q, H)

**Q-01 (primary):** Does Configuration B provide at least 25 seconds more usable warning time than Configuration A under matched threat and condition cells?
- **H-01:** Under the tested threat and conditions, Configuration B increases paired usable warning time by at least 25 seconds relative to Configuration A.
- Null condition: paired increase < 25 s or too uncertain to support the customer decision.
- Prediction recorded before execution: Config A median usable warning time 70–90 s; Config B median 110–140 s; predicted paired increase 35–55 s.

**Q-02:** Does the added layer produce a decision-ready C2 track without an unacceptable handoff penalty?
- **H-02:** Configuration B maintains at least 90% usable handoff success in the tested core cells and adds no more than 1.0 second to the 90th-percentile source-to-C2 latency.
- Prediction: handoff success 90–98%; added 90th-percentile latency 0.3–0.8 s.

**Q-03:** Does the added layer preserve track quality?
- **H-03:** Configuration B does not reduce median track continuity by more than 0.03 and does not increase opportunity-level position RMSE above 50 m.

**Q-04:** Which geometry creates the smallest warning benefit or the highest failure rate?
- Prediction: the sector-boundary approach will produce the smallest benefit and the highest handoff uncertainty. (No hypothesis; exploratory question.)

**Q-05:** Does Configuration B create enough time for the represented engagement chain?
- **H-05:** Configuration B produces a positive mission margin in at least 80% of valid end-to-end confirmation opportunities under the tested core condition.

### 1.8 Customer decision rules (advance/no-advance thresholds)

Configuration B advances to the next phase if:
1. Estimated paired warning-time increase is at least 25 seconds.
2. The uncertainty interval does not indicate a material negative effect.
3. Median warning time is at least 90 seconds in the core condition.
4. Track continuity loss is not greater than 0.03.
5. Position RMSE remains at or below 50 m.
6. Added 90th-percentile handoff latency is at or below 1.0 second.
7. No unresolved failure prevents the engagement chain from using the early track.

Rule: a threshold miss in one geometry can result in a restricted recommendation instead of complete rejection.

## 2. Calculations & formulas

### 2.1 Measure definitions instantiated for this campaign (M-01 .. M-10)

The app instantiates definitions from the controlled C-UAS measure library (agent 9 owns the full dictionary); the campaign-local forms are:

**M-01 — Usable warning time** (primary):
```
Usable warning time = truth boundary-crossing time − decision-ready C2 track time
```
Experimental unit: one independently reset threat presentation.
Decision-ready track requires ALL of: correct truth-object association; required position and velocity fields; track age within 1.0 second; position-quality state within the customer criterion; C2 track persistence for at least three consecutive updates.

**M-02 — Paired warning-time improvement:**
```
Paired improvement = warning time for Configuration B − warning time for Configuration A
```
Constraint: pairs must use the same threat profile and factor cell within the same test block.

**M-03 — Probability of detection:**
```
Probability of detection = valid opportunities with a valid detection / total valid detection opportunities
```
Report by range band, altitude, azimuth, speed, and configuration.

**M-04 — First-stable-track range:** truth-derived distance from the threat to the protected boundary when all stable-track rules first pass.

**M-05 — Track continuity:**
```
Track continuity = eligible time with a valid associated track / total valid eligible tracking time
```

**M-06 — Opportunity-level track error:**
```
Error(t) = blue position(t) − truth position(t)
RMSE = sqrt[sum(error_i²) / m]
```
Rule: matched updates within one run support one opportunity-level summary; they do NOT count as independent tests.

**M-07 — Handoff success:**
```
Handoff success = qualifying source tracks that become usable C2 tracks / valid qualifying source-track opportunities
```

**M-08 — Source-to-C2 latency:**
```
Latency = decision-ready C2 event time − qualifying source-track event time
```
Rule: a failed handoff is censored or failed under the approved rule; it is NOT assigned the timeout as a completed latency.

**M-09 — False or nuisance track rate:**
```
False-track rate = adjudicated false or nuisance tracks / valid surveillance hours
```

**M-10 — Mission margin:**
```
Mission margin = usable warning time − required action-chain time − uncertainty reserve
```

### 2.2 Mission-time requirement (computed at DESIGN time)

```
Required chain time = 8 + 4 + 8 + 55 + 5 = 80 s
Required warning threshold = 80 + 10 = 90 s
```

Example warning calculation (distance / speed form): threat 3,600 m from boundary at decision-ready, measured ground speed 30 m/s:
```
Usable warning time = 3,600 m / 30 m/s = 120 s
Mission margin = 120 − 80 − 10 = 30 s
```
Scope caveat: a positive margin supports only the tested timeline (not a faster threat, another route, another effector, or another C2 procedure).

### 2.3 Paired sample-size approximation (planning stage)

```
Approximate paired sample = [(z_alpha + z_power) × sd / min_effect]²
= [(1.96 + 0.84) × 30 / 25]²
= [2.80 × 1.20]²
= 3.36²
= 11.29
```
Round up to 12 valid pairs for the first comparison stage. Rule: this is a planning approximation; the analysis lead completes the final power or simulation check before issue.

### 2.4 Valid-run allowance

```
Required scored attempts = target valid / expected valid fraction = 48 / 0.80 = 60 attempts
```
Plus 4 control/rehearsal opportunities outside the primary comparison. Maximum planned activity: 64 opportunities.

### 2.5 Matrix arithmetic

```
3 azimuths × 2 altitudes × 2 speeds = 12 condition cells
Stage 1: 12 cells × 2 configurations = 24 valid opportunities
Stage 2: 8 cells × 2 configurations = 16 valid opportunities
Stage 3: 8 Configuration B opportunities
Total: 24 + 16 + 8 = 48 valid scored opportunities
```

### 2.6 Common-time (latency) uncertainty budget

Illustrative source uncertainties: start timestamp 0.02 s; stop timestamp 0.02 s; synchronization 0.01 s; event definition 0.03 s.
```
u_latency = sqrt(0.02² + 0.02² + 0.01² + 0.03²) = sqrt(0.0018) = 0.042 s
Along-track uncertainty at 30 m/s = 30 m/s × 0.042 s = 1.26 m
```
Rule: the latency measure needs time uncertainty below the smallest meaningful timing difference. The Workbench flags a source if its timing state makes a required measure unavailable.

### 2.7 Result-stage statistics (illustrative, but the calculation types are canon)

- Valid-run rate: `48 / 58 = 0.828 = 82.8%`
- Threshold-meet proportion with approximate 95% Wilson interval: `18/20 → 0.90 (0.70 to 0.97)`; `25/28 → 0.893 (0.73 to 0.96)`; `3/20 → 0.15`
- 95% bootstrap interval on median paired improvement: 35 to 57 s (point 46 s)
- Mission margins: `A: 76 − 80 − 10 = −14 s`; `B: 123 − 80 − 10 = +33 s`
- Range-to-time conversion: `1,410 m / 30 m/s = 47 s` (cross-check of warning gain against stable-track range gain)

### 2.8 Sensitivity calculations (ASSESS stage)

Faster threat (distance held at 3,690 m, speed 30 → 35 m/s):
```
Warning time = 3,690 / 35 = 105.4 s
Mission margin = 105.4 − 80 − 10 = 15.4 s
```
Longer engagement (represented time to effect +20 s):
```
Revised required chain = 80 + 20 = 100 s
Revised requirement with reserve = 100 + 10 = 110 s
Configuration B median margin = 123 − 110 = 13 s
Configuration A median margin = 76 − 110 = −34 s
```
Unknown-outcome handling: keep primary, best-case, and worst-case treatments of anomalous runs visible (if the 3 Config B handoff anomalies are excluded, the estimate becomes artificially favorable).

## 3. Checklists

### 3.1 Card "Required state" checklist (pre-run, run crew)

- Tracking radar, C2, operator procedure, threat profile, and engagement timing are unchanged within the pair.
- Stale tracks and queues are cleared.
- Configuration manifest matches the selected A or B state.
- Truth, sensor, adapter, C2, environment, and run log are healthy.
- Clock offset is within the measure limit.

### 3.2 Run-specific hold conditions (test conductor; hold before the run if any is true)

- Configuration state is unknown.
- Truth or common time is not healthy.
- Queues or tracks from the prior run remain.
- Threat route, altitude, or speed cannot meet the cell tolerance.
- A required source is unavailable.

Governance hook (one line): general safety and range stops remain in the active field plan; they are not repeated in full on the card.

### 3.3 Run-ordering rules (schedule generator)

- Pair A and B within the same day and weather block.
- Reverse pair order across blocks.
- Do not change altitude and azimuth at the same moment when the result would be difficult to diagnose.
- Clear queues and stale tracks before each run.
- Require a full configuration check after every A/B switch.
- Hold confirmatory opportunities until screening identifies the final core condition.
- Separate exploratory augmentation from confirmatory evidence.

### 3.4 Preapproved adaptation rules (day-of, conditional logic)

- IF required truth, configuration, or timing fails THEN repeat the run.
- IF a handoff failure appears twice in the same geometry THEN add one diagnostic pair.
- IF the observed warning margin is within ±10 seconds of zero THEN add one boundary cell.
- IF the minimum valid sample exists and more runs are unlikely to change its interpretation THEN stop that cell.
- ALWAYS preserve at least eight Configuration B opportunities for final confirmation.
- NEVER use an exploratory diagnostic run as confirmatory evidence.

Rule: keep each adaptation inside an approved rule and preserve the original and revised run lists.

### 3.5 Data-validity rules (per-run, automated + data monitor)

A run can support usable warning time only if ALL hold:
- Truth covers the complete opportunity.
- Threat speed, altitude, and route remain inside tolerance.
- Configuration IDs are known.
- Decision-ready and boundary events are reconstructable.
- Object association is unambiguous.
- Common time passes.
- No critical data gap overlaps either event.

Key rule: a run may remain valid for detection probability but become invalid for latency — validity is assigned BY MEASURE, not only by run.

### 3.6 Stage 0 method controls (4 opportunities)

- Positive control for known favorable detection.
- Negative or background-only surveillance interval.
- Full data-chain rehearsal.
- Configuration-switch and reset rehearsal.

### 3.7 Baseline ideal standard (campaign-completeness checklist)

A baseline ideal campaign is complete when:
- The customer question is measurable.
- The test object and exact change are explicit.
- The hypothesis can be supported or contradicted.
- Predictions exist before results.
- The experimental unit is correct.
- The factor space supports the intended claim.
- Repetitions trace to a quantitative reason.
- Every measure has independent truth and required data.
- The card contains only execution-critical content.
- The day-of interface captures actual conditions and events.
- Calculations are reproducible.
- Uncertainty and trade-offs remain visible.
- The finding states both the result and its limit.
- The customer receives a practical action and next test.

## 6. Workflow & sequencing logic

### 6.1 Canonical end-to-end flow (the user journey)

```
Customer question → test object → measures → hypotheses and predictions → method
→ factor space → matrix → test cards → day-of execution → calculation → finding → customer action
```

Case-study phase names in order: DEFINE (customer need/test object; threat/vignette) → DESIGN (questions, hypotheses, predictions; sample and matrix) → QUANTIFY (measures and decision rules) → CALCULATE (mission-time requirement) → PREPARE (instrumentation/data plan; schedule; lean card) → ISSUED CARD → EXECUTE (day-of view; adaptive daily logic) → ASSESS (results; sensitivity; hypothesis evaluation) → DEBRIEF (customer finding) → ACT (recommendation).

### 6.2 Decision-backward planning logic (real-world JIATF-401 origin)

```
Government decision → questions that must be answered → measures that answer those questions
→ data needed to calculate the measures → test conditions needed to produce the data
→ runs and flight profiles → findings and remaining gaps
```

### 6.3 Sequential design stages

- Stage 0 — Method controls: 4 opportunities (list at 3.6).
- Stage 1 — Screening comparison: 12 condition cells; one matched A/B pair each; A/B order randomized within each block and balanced for which configuration runs first; 24 valid opportunities.
- Stage 2 — Focused augmentation: 8 cells by preapproved rule (4 highest-uncertainty cells; 2 smallest-margin cells; 2 cells needed to distinguish a geometry effect from an interface effect); one more matched A/B pair each; 16 valid opportunities.
- Stage 3 — End-to-end confirmation: 8 Configuration B opportunities under the selected operational core condition, full represented chain through engagement readiness and effect timing.

### 6.4 Evidence chain (instrumentation gate)

```
Physical threat event → independent truth → sensor and C2 events → common time and identity → validated measures → bounded finding
```
Independent truth, common time, calibration, and measure-level validity are prerequisites for detection range, track error, latency, and warning claims.

### 6.5 Preparation schedule (working-day countdown)

- T-30 to T-21: conduct customer discovery; freeze the primary decision and questions; identify the exact system builds; select threat profiles; load prior evidence; build the first measure set; identify required source fields.
- T-20 to T-14: connect source feeds; verify identifiers and clocks; register sensors and truth sources; validate threat flight profiles; run Configuration A and B bench checks; test queue and state reset.
- T-13 to T-8: freeze factor space; run sample-size review; generate the matrix; generate cards; compute every primary measure from rehearsal data; correct data and interface defects.
- T-7 to T-2: conduct full field rehearsal; validate positive and negative controls; dry run the A/B change process; verify the tablet workflow; freeze the issued matrix and first-day cards.

### 6.6 Field-day rhythm (6 days)

- Day 1: execute controls; run the first four A/B pairs; validate the warning-time and handoff calculations.
- Day 2: continue screening pairs; cover remaining core geometries; review variation and invalid-run causes.
- Day 3: complete the 12 screening pairs; select focused augmentation cells.
- Day 4: execute focused A/B pairs; isolate sector-boundary and handoff effects.
- Day 5: complete focused augmentation; freeze the confirmatory Configuration B condition.
- Day 6: execute end-to-end confirmation; use reserve time for validity repeats only.

### 6.7 Adaptive daily cycle

Case-study controlled sequence:
```
Run → validate → calculate → compare with prediction → update evidence gap → select the next approved cell
```
Real-world JIATF-401 cycle:
```
Run the planned tests → review the collected evidence → identify open data gaps
→ determine which gaps matter to the decisions → create the next day's plan → collect the missing evidence
```
Contrast stated in source: this replaces "blindly following a static card"; each day's results change the priority of the next day's work (sequential test planning). Adaptations must stay inside preapproved rules (3.4) and both original and revised run lists must be preserved.

## 8. Product implications

The case study's section 19 is an explicit product requirement list; the app must:
- Convert vague customer language into quantified questions (guided clarification-question flow, 1.2).
- Suggest a defensible method (engagement-type selection: characterization / comparison / threshold verification / all three).
- Build measures with correct events and denominators; instantiate from a measure library by reference, not by copying formulas onto cards.
- Connect each measure to required data (data-field manifest per source; source-health flags; validity by measure).
- Generate a test matrix from factors and sample logic (factorial cell generation, paired-sample calculator, valid-run inflation, stage structure, randomized and balanced A/B ordering).
- Compile a short executable card from linked records (lean-card compiler: control ribbon, intent, required state, numbered procedure, event marks, hold conditions, preliminary use rule; everything else by record ID).
- Capture planned and actual test state (actual-condition capture, deviation/anomaly forms).
- Calculate quick-look and final measures (post-run quick look within minutes; final analysis separate).
- Preserve valid failures; separate invalid evidence from poor system performance (4-state preliminary use rule; measure-level validity).
- Compare predictions with results (predictions recorded before execution; prediction-versus-result view).
- Identify the remaining evidence gap (valid-evidence-by-cell coverage map; open gaps; next-run recommendation under preapproved adaptation rules).
- Convert the result into a practical customer action (bounded finding + restricted recommendation + corrective work + next test package as a regression package).

Concrete build directives derived from sections 1–7:
1. Seed campaign: implement `J401-EW-01` end to end as shipped demo data — campaign record, Q/H/prediction set, M-01..M-10, 12-cell matrix, 4-stage design, card `TC-J401-EW-COMP-01-v1.0`, the 6-day schedule, and the full illustrative results in 7.2 as fixtures for every calculation.
2. The user journey is the section flow in 6.1: DEFINE → DESIGN → QUANTIFY → CALCULATE → PREPARE → ISSUE → EXECUTE → ASSESS → DEBRIEF → ACT. Navigation and progress should mirror it.
3. Variables need four first-class classes (independent, screened factor, held control, recorded covariate) plus nuisance risks with assigned mitigations (blocking, reset, randomization, capture).
4. Decision rules are structured records (threshold + direction + measure), evaluated automatically against results, with support for a "restricted recommendation" outcome on partial miss.
5. Event marks are a per-card ordered vocabulary rendered as large tap targets on the tablet current-run screen; timestamps from them feed M-01, M-04, M-08 directly.
6. Uncertainty is first-class: bootstrap interval on paired medians, Wilson interval on proportions, timing uncertainty budget (RSS), and primary/best-case/worst-case treatment of anomalous runs.
7. Sensitivity tools: recompute warning time and margin under changed speed and changed chain-time assumptions (simple algebra on stored inputs).
8. Exports: Excel, CSV, JSON, PDF, and print for the after-execution package; tablet-ready day-of views.
9. Real-system library entries to seed: Picogrid C2, RADA RPS-42, CHAOS Vanquish, Merops interceptor, Mugin-3 red air, Bumblebee, Hornet (specs at 1.12; sparse — mark unverified).
10. The "immediate evaluation output, not a PDF 60–90 days later" contrast and the replayable data record are the core value propositions the module must demonstrate.
