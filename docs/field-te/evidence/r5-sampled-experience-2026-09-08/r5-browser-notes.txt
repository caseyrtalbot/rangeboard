Runtime files
All artifacts go under the chosen out directory, created recursively at runtime:
r5-browser.json, retained-trial.json, export.json, execute-ready.png,
execute-paused.png, execute-complete.png, analyze-complete.png, compact-ready.png,
and compact-complete.png. A failed check may prevent its optional artifact.

r5-browser.json always uses status 'captured'; this is NOT a pass verdict. Inspect
all 15 named checks and the exit code. Any failed check exits 1. Page errors and
console errors fail the final check, including errors arriving during shutdown.
Console warnings are retained for interpretation without automatically failing.
The top-level commit is git rev-parse HEAD, not proof of clean-tree provenance.
fixtureSha256 hashes the original fixture bytes, not the later in-memory export
configuration. The Chromium field records browser.version().

Execution bounds and failure handling
Each check has its own try/catch and reports {name, pass, detail}. Assertion
failures do not stop later checks. Explicit wait timeouts are capped by each
check's remaining budget; an outer per-check timer also bounds evaluate/imports
and browser operations without native timeout options. A check timeout closes
the context to stop abandoned operations; subsequent checks still attempt their
prerequisites and report that the browser is unavailable. Startup failures are
likewise reported individually for all 15 checks, never represented as executed
browser assertions.

Browser work has a 210-second budget. A separate Node supervisor checkpoints IPC
reports and enforces a 230-second worker wall-clock limit, below four minutes
including its bounded git lookup. It can stop a stuck evaluate/browser process,
write failed prerequisite entries for missing checks, and kill only its own
detached child process group. Both normal cleanup waits are bounded to one second.
The deadline is an execution ceiling, not a promise that every assertion will
finish successfully on a slow machine. No server process is killed.

Interpretation and inspection seams
Engagement lanes represent threat tracks with paths, not formation members and
not events. Above 14 tracks the UI groups related names; the harness expands
groups and counts leaf lanes separately from aggregate headings. Shot marks
represent each track's first assignment. Arrival diamonds are reached arrivals,
not successful-effect counts.

Ledger rows appear at assignment time tS. A row can legitimately exist while
tEffectS is still future. Its effect time, P, and Removed value must remain an
em dash until the shared horizon reaches tEffectS. Planned arrival/CPA, the
transport duration, and the engagement strip's full planning axis are not future
effect leakage. Time-series outcome axes are separately required to end no later
than the horizon. Selector/readout comparisons verify consumer agreement, not
independent numerical validation of the sampled engine.

Measured/held-between-scans sensors light rings; coasting sensors can remain in
the held-track KPI/readout but do not light rings. Equality with deterministic
detections at one instant is allowed and explicitly recorded. No difference is
manufactured by changing seeds or retrying until a desired sampled outcome.

Long Task observations have a 50 ms floor. A zero count does not establish a
sub-50-ms maximum, smooth frame rate, or a performance threshold. perf-play is
a bounded capture with transport assertions, not a fabricated performance gate.

The script uses the existing window.Konva instance, never imports a second copy.
Chart domains/FX marks are read from the committed React tree for actual mounted
TimeSeriesPlot components because axis tick labels alone cannot prove the domain
endpoint. These are development inspection seams; their absence is a failure.
This is not pixel-based interpretation of every shape. Screenshots are saved for
human visual review, and the script does not claim they were visually approved.

The fresh context standardizes Run summary plus an event-ledger widget, exposes
track telemetry, and uses sensor ring overrides for inspection. These changes
are browser presentation state only. Export alone changes run settings as noted;
screenshot capture restores the original fixture. Nothing changes the fixture
file, source files, another browser profile, or any running server.
